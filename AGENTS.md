# AGENTS.md

Guide for anyone (human or coding agent) working on this repository: how the app works, the rules to follow,
and what comes next. User-facing documentation lives in `README.md`.

## What the app does

A single-page app to play timed games against Stockfish with an AI coach. After each user move, a second engine
judges the move. If it is an inaccuracy, a mistake or a blunder (at or above the threshold chosen in the
settings), the clock stops and the coach explains it: a hint first, then the best move, the engine's refutation
and the positional idea. The user can retry the move, show the solution, or continue. The coach also flags the
engine's own errors when the user fails to punish them.

Everything runs in the browser. There is no backend: the engine is WebAssembly, the AI coach is called directly
from the browser with the user's own API key, and data is kept in browser storage.

## Stack

- Vite 8, Vue 3 (`<script setup>`, Composition API), TypeScript (strict), Pinia.
- [chess.js](https://github.com/jhlywa/chess.js) for the rules, [chessground](https://github.com/lichess-org/chessground)
  for the board, the `stockfish` npm package (Stockfish 19 lite, single-threaded WASM).
- Vitest for unit tests, ESLint (typescript-eslint, eslint-plugin-vue) and Prettier.
- Node 22 (`.nvmrc`), Node 20 minimum.

## Commands

```bash
npm install

npm run check            # lint + typecheck + unit tests
npm run build            # typecheck + production build into dist/
```

Run `npm run check` and `npm run build` before opening a pull request. CI (`.github/workflows/ci.yml`) runs
lint, typecheck, tests and build on every push to `main` and on every pull request.

## Conventions

- **Language**: code, identifiers, file names, comments and docs in English. Everything the user sees in the UI
  is in French (including coach prompts, which ask for French answers).
- **Git**: never commit on `main`. Work on a branch and open a pull request.
- **Commit messages**: lowercase except proper nouns and acronyms (`add board color themes`, `fix OpenAI
streaming`), short and readable. No co-author trailers, no "generated by" lines. Same for PR descriptions:
  concise, written for humans.
- History rewrites and force pushes need the owner's explicit approval.
- Formatting: Prettier (single quotes, print width 110, trailing commas). Use the `@/` alias for imports from
  `src/`.
- Licensing: the project is GPL-3.0-or-later because Stockfish and chessground are GPL. Any asset added (piece
  sets, sounds, fonts) must allow commercial use and be GPL-compatible. Non-commercial (NC) or "freeware" assets
  are not allowed. Credit every asset in `public/pieces/CREDITS.md` or an equivalent file.

`src/chess`, `src/engine/levels.ts`, `src/game/analysis.ts` and `src/coach/sections.ts` are pure functions and
are where most unit tests live. Keep new logic there when it can be tested without a browser.

## How it works

### Engines

`src/engine/engine.ts` runs Stockfish in a web worker and serializes searches (one at a time, with stop and
cancellation). It tries, in order: the WASM build, the WASM build from a blob URL, then the asm.js build (slow
fallback). `scripts/copy-stockfish.mjs` copies the build into `public/stockfish/` (not committed) and patches
`WebAssembly.instantiateStreaming` into `arrayBuffer` + `instantiate`, so the engine loads even when the host
serves `.wasm` with the wrong MIME type.

Two engine instances run during a game:

- **Player**: plays the opponent's moves. `src/engine/levels.ts` defines 20 levels (depth, number of candidate
  lines, softmax temperature in centipawns, chance of a random candidate or a random legal move). Levels are not
  calibrated against human ratings.
- **Analyst** (`src/game/analyst.ts`): full strength, 3 lines (MultiPV), up to depth 16 or 20 s. It analyses the
  user's position while they think and caches the deepest result per FEN, so judging a move is usually instant.

### Game flow

`src/stores/game.ts` owns the game. Its `phase` is one of `setup`, `user`, `checking`, `coaching`, `engine`,
`advice`, `over`. A `token` is bumped on every new game, reset or undone "Continuer"; async callbacks check it
and stop if it changed.

1. `user`: the clock runs, the analyst analyses the current position.
2. On a move, `onUserMove` stops the clock and goes to `checking`. `evaluateUserMove` compares the analyst's
   best line with the score after the move (taken from the matching line, or from a new search on the resulting
   position).
3. `judgeMove` (`src/game/analysis.ts`) classifies the move the way Lichess does, from the drop in winning
   chances `2 / (1 + e^(-0.00368208 * cp)) - 1`: blunder ≥ 0.3, mistake ≥ 0.2, inaccuracy ≥ 0.1 with at least
   30 cp lost. Missing a mate in 3 or less counts as at least an inaccuracy.
4. If the move is an issue at or above the threshold, the game goes to `coaching`: hint arrows on the board,
   coach request, then retry / solution / continue. Otherwise the clock gets its increment and the engine plays
   (`engine`). "Continuer" can be undone (`undoContinue`, "Revenir à l'erreur") while the engine thinks or
   after its reply until the user moves again (`continueUndoStage` in `src/game/undo.ts`): the engine search is
   stopped or its reply taken back, the clock is put back as it was during the pause, and coaching resumes.
5. `opponentErrorClass` detects when the engine's last move gave the user a big chance (gain in winning chances
   ≥ 0.2 or 0.3, at least 80 cp, user at least 45% win). If the user then misses it, the coach points it out.
6. `advice` is the on-demand "Conseil" button during the user's turn. `over` shows the review, the AI summary
   and the PGN.

Accuracy uses the Lichess formulas (`moveAccuracy`, `gameAccuracy` in `src/chess/evaluation.ts`). Statistics
are computed on **first attempts**: a retried move still counts with its original judgement, so take-backs do
not inflate the accuracy. The adaptive level (`adaptLevel`) moves +1 after a win, +2 after a clean win (no
blunder, accuracy ≥ 85%), 0 after a win that needed a blunder take-back, −1 after a loss.

History browsing: `viewPly` selects a past position. The board always renders the computed `BoardView`
(position, last move, arrows, whether the user can move), never the live chess.js object directly.

### AI coach

- `src/coach/prompts.ts` builds three prompts: an error explanation (`mistakePrompt`), on-demand advice
  (`advicePrompt`) and the end-of-game summary (`summaryPrompt`). Answers are asked in labelled sections that
  `src/coach/sections.ts` parses while streaming. When the model ignores the labels, the raw text is shown.
- **Grounding**: the model must not compute chess facts. Engine lines, evaluations, hanging pieces and attack
  tables (`src/chess/attacks.ts`: attackers and defenders per square, batteries behind bishops/rooks/queens,
  absolute pins excluded, relative pins noted) are computed by code and given in the prompt, with explicit rules
  to count only from these tables and to mention only moves present in the engine lines. Any new prompt must
  keep these rules.
- Providers (`src/coach/providers/`): Anthropic (browser access header), OpenAI Chat Completions (base URL
  configurable, browser CORS not guaranteed), Google Gemini (`streamGenerateContent`, SSE), and the claude.ai
  artifact runtime (`window.claude`, only when the app runs as an artifact). Provider `auto` prefers the
  claude.ai runtime, then the first provider with a key. Default model ids are in `providers/types.ts`.

### Storage

- Settings and game history: `src/storage/profileStore.ts`. localStorage (`chess-coach.settings`,
  `chess-coach.games`, 50 games max), or the artifact database when running as a claude.ai artifact.
  `sanitizeSettings` validates everything read back, so old or corrupted data never breaks the app.
- API keys: `src/storage/apiKeys.ts`, in localStorage only when "remember" is checked, otherwise in
  sessionStorage. Never stored with the settings or game history, never sent anywhere except the chosen
  provider.
- A saved game is a `GameRecord` (PGN and statistics, in the game list) plus its `GameDetails`
  (`src/game/details.ts`): the issues with the coach's answers, the engine's errors, the full statistics and
  the end-of-game summary. Details are stored apart, one localStorage entry per game
  (`chess-coach.details.<date>`, or `details/<date>` in the artifact database), keyed by the record's `date`.
  They are saved when the game ends and again once the coach's pending answers and the summary complete. When
  localStorage is full, the oldest details are dropped first; the records stay. `sanitizeDetails` validates
  them on load. Games saved before details existed replay with their moves and statistics only.

### Appearance

`src/appearance/themes.ts` holds the board color presets and the piece set list. `applyAppearance` sets the
`--board-light` / `--board-dark` CSS variables (the board is drawn with a CSS conic gradient in
`src/styles/board.css`) and injects one `<style>` with the piece images of the chosen set. To add a set: put the
12 SVGs in `public/pieces/<id>/`, add it to `PIECE_SETS` with author and license, and credit it in
`public/pieces/CREDITS.md`. A unit test checks that every listed set has its 12 files.

## Testing

- Unit tests: `tests/unit/*.test.ts` (Vitest, Node environment, `tsconfig.test.json` for Node types).
- There are no end-to-end tests in the repository yet. Browser checks so far were done by hand or with ad hoc
  Playwright scripts kept outside the repo.
- AI providers were only tested against simulated responses, not real API keys.

## Known limitations

- Engine levels are not calibrated against Elo; level 9 is not "1500".
- Even with grounding, the coach can still be wrong in its explanations. The UI says so in the footer.
- OpenAI does not guarantee direct browser calls (CORS); if they fail, a relay or an OpenAI-compatible service
  is needed (the base URL is configurable).
- The analyst stops at depth 16, which is enough to judge club-level moves but not deep tactics.

## Next steps

### 1. Put the app online

Done: the repository is public, GitHub Pages deploys `main` (`.github/workflows/pages.yml`), production builds
carry a Content Security Policy meta tag (`vite.config.ts`), and the footer links to the source and says where
keys and games are kept.

About the CSP: GitHub Pages cannot send headers, so the policy is a `<meta>` tag added at build time (not in
dev, not in the artifact build). `script-src 'self' 'wasm-unsafe-eval'` refuses any injected script, which is
what protects the API keys. `connect-src` stays open to `https:` and local servers because the OpenAI base URL
can point to any relay; `style-src` needs `'unsafe-inline'` for the piece-set `<style>` from `applyAppearance`.
`frame-ancestors` cannot be set from a meta tag. The WASM engine and its blob-worker fallback were checked under
the policy.

Left:

- **Real-key check.** Play a few games with each provider and a real key: default model ids, streaming,
  error messages (invalid key, quota, CORS), and the model list in the settings.
- Optional: a domain name.

### 2. Game history and review

Done: "Revoir" on each row of the history card opens the game on the game screen in a read-only replay
(`openReplay` in the game store, `phase` `over` with `replay` set): move list with markers, history browsing,
the end-of-game panel with its summary, and each error with the coach's explanation. See Storage above.

Left:

- **Re-analysis.** Games without details (or with the coach disabled) could be re-analysed on demand with the
  analyst engine; ask the coach again only when the user clicks, since it costs API calls.
- **Accuracy graph** along the move list, from per-move evaluations (not stored yet: `moveEvals` would need to
  go into the details).
- Only the 8 most recent games are listed; older ones are stored but not reachable from the UI.

### 3. Exercises from the user's own mistakes

Goal: turn each mistake into a puzzle that comes back later (spaced repetition), so the user trains on the
positions they actually get wrong.

- **Source.** Every issue already has what a puzzle needs: `fenBefore`, the move played, `bestUci`, the
  class and the top engine lines. Missed engine blunders (`issue.opp`) make good "punish it" exercises. Start
  with mistakes and blunders; inaccuracies are often too subtle for a puzzle.
- **Card.** `{ id, fen, played, best, cls, theme?, createdAt, dueAt, interval, streak }`, deduplicated by FEN.
  Store under its own key (`chess-coach.drills`) or artifact collection, independent of the game history.
- **Answer check.** Do not require the exact engine move: accept any move whose loss in winning chances is
  under 0.1 compared with the best one (the same scale as `judgeMove`), re-checked with the analyst. Then show
  the engine's line.
- **Scheduling.** Simple Leitner-style intervals: 1, 3, 7, 14, 30 days. A correct answer moves to the next
  interval, a wrong one goes back to 1 day. Retire a card after it is solved at 30 days.
- **UI.** On the setup screen, "N exercices à revoir" opens a session: position, side to move, no clock,
  hint button (reuse the coach with the stored explanation, or a new short prompt), retry or show the solution.
  Optionally offer the due exercises before starting a new game.
- **Tests.** Scheduling logic, answer acceptance against stored lines, deduplication.
